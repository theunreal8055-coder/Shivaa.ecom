# DEPLOY v117 — "Butter": Speed Release + Hero Slider Button Fix

## What this fixes

### 1. Hero banner slider buttons "shift to the bottom of the page when clicked" (FIXED)
- **Root cause A — focus scroll:** the banner slider is keyboard-focusable (`tabindex="0"`) and the ‹ › controls are real `<button>` elements. Every tap — on a dot (focus delegates to the slider), an arrow (focuses the button), or a slide — made the browser **scroll the page until the whole 430–600 px banner was in view**. That scroll is what looked like the buttons moving to the bottom of the page.
  - **Fix (js/app.js):** `pointerdown` on the slider now calls `preventDefault()`, refusing the focus hand-off. Taps, swipes, dot clicks and link clicks all still work; keyboard users still reach the slider with Tab (where scrolling to it is correct).
- **Root cause B — press jump:** `aurum.css`'s press feedback (`transform: scale(.9)`) **replaced** the arrow's centring transform (`translateY(-50%)`), so while a thumb held an arrow it visibly dropped by half its height.
  - **Fix (css/v117.css):** the pressed state keeps the centring transform and adds the squash on top: `translateY(-50%) scale(.92)`.
- **Bonus:** the track now moves via GPU-composited `translate3d` instead of `translateX` — visibly smoother slide changes on mid-range Android.

### 2. Website speed — butter-smooth, mobile-first (OPTIMISED)

**First paint (the biggest wins):**
- **Fonts: 354 KB render-blocking stylesheet → 2 KB stylesheet + 3 real woff2 files (78 KB).** The old `fonts.css` embedded the same font 2–4× as base64. It fully blocked first paint; on 4G that alone could hold every word hostage for seconds. Fonts are now preloaded in parallel and never block painting (`font-display: swap`) — the page shows immediately in the system font and swaps into the house fonts as they land. Rendering is byte-identical (same files that were embedded).
- **~200 KB of CSS no longer blocks the first screen.** Hallmark, Trust, motion, aurum, v107 and boost stylesheets now load via the non-blocking preload pattern (with `<noscript>` fallbacks). Only the shell CSS the opening screen truly needs stays render-blocking.
- **~110 KB of JavaScript (aurum + motion + boost) moved after first paint.** `js/v117.js` injects them once the first screen is up, in the same order as before. They register no routes and are all written to be safe when absent.

**Boot time:**
- Boot used to wait through **three serial network rounds** (5 API calls → rates → footer pages) before lifting the preloader. Now **one parallel batch** carries everything (rates included), the footer page-links hydrate in the background, and a hard 6-second cap lifts the splash no matter what (15 s on post-login redraws). If a very slow network loses to the cap, the shop re-paints itself the moment the data lands — never a blank or frozen splash.

**Scrolling / general:**
- Below-the-fold sections (from the 5th down) and the footer get `content-visibility: auto` on smaller screens — the phone skips laying out and painting what you haven't scrolled to yet.
- The desktop-only cursor glow no longer burns GPU on phones.

## Deploy steps

1. Extract `shivaa-update-v117.zip` into Hostinger `public_html/` (it keeps the
   folder layout: `index.html`, `sw.js`, `js/…`, `css/…`, `fonts/…`).
2. That is the whole deploy — the auto-sync cron also pulls the same tree from
   the GitHub `main` branch within ~5 minutes of the merge.
3. **On your phone afterwards (important):** close ALL Chrome tabs of
   shivaa.in and reopen fresh (or pull-to-refresh twice). The old shell +
   new script pairing reloads itself once automatically now, but a stale
   tab can still sit on yesterday's code until it is closed.
   Last resort: Site settings → Clear & reset.

## Rollback

Re-upload the v116 zip (`shivaa-update-v116.zip`) — no data/database changed
in this release; it is presentation and boot-order only. The new `fonts/`
folder can simply stay on the server unused.
